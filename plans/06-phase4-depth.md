# Phase 4 — Depth on both tracks

Depends on: Phase 1 transports and Phase 3 probe map. Phase 2 is needed for the gray-box context UI.
Parent: [00-master-plan.md](00-master-plan.md). This phase implements coverage-spec layers 1–4 and 6–7 in part, plus classic API/SAST/SCA.
Spec: [01-ai-redteam-coverage-spec.md](01-ai-redteam-coverage-spec.md) sections 3.1, 3.2, 3.5, 3.6, 3.8 and the oracle table in section 4.

Tracks 4A and 4B can proceed in parallel after the oracle result type exists.

## Goal
Black-box chat probes stop being the whole AI product. Gray-box context, multi-turn attacks, indirect injection, and RAG planting are real scans. Classic scanning covers authenticated APIs, code, secrets, and dependencies. Oracles decide pass/fail.

## Exit
- On a benchmark app we control, a gray-box AI scan (system prompt + tool schemas provided) reports more confirmed findings than the Phase 1 black-box profile, measured by canary oracles, not by finding count alone.
- An authenticated API scan finds a planted BOLA/IDOR.
- A repo upload (artifact only) yields a secret finding whose value is not stored, plus a dependency CVE from osv-scanner.
- Attacker prompts are generated by our self-hosted model. A commercial API is not on the attack-generation path.
- Judge false-positive rate on a labeled calibration set is recorded and below an agreed ceiling (set the ceiling when the set exists; do not ship without the number).
- Owned matrix cells are green ([17-test-suite.md](17-test-suite.md)).

## Out of scope
The autonomous chaining agent (Phase 5), MCP honeypots (Phase 7), full white-box code graph (Phase 8). Tree-sitter in 4B is limited to secrets-adjacent and a few sink rules; Phase 8 deepens it.

## Shared: oracle framework
A finding is not "the judge said yes". Each probe declares one or more oracles:

| Oracle | Pass condition |
| --- | --- |
| canary | planted token appears in output or tool args |
| tool_trace | a forbidden tool, arg, or sequence occurred |
| goal_diff | original task failed and the attacker's goal succeeded |
| policy_judge | classifier or judge model flags a policy breach, with a confidence |
| structural | deterministic parse (HTML sink, exposed embedding endpoint) |
| resource | token, cost, latency, or loop budget exceeded |
| acl | cross-tenant or cross-doc object returned |
| manifest_drift | hash or schema differs from the pin |
| state | a later turn still obeys an earlier planted instruction |

Store `oracle`, `oracle_pass`, and `confidence` on the finding. `policy_judge` alone cannot mark severity critical. Critical requires a deterministic oracle (canary, tool_trace, structural, acl) or two independent signals.

Calibration set: 50+ labeled cases (true leak, true refusal, benign lookalike). Run in CI nightly, not on every PR. Track precision. Humans can mark `false_positive` in the UI; that label feeds the next calibration review, it does not auto-retrain.

## Track 4A — AI depth

### More engines, same relay
- PyRIT worker image: `PromptChatTarget` subclass that calls the hub. Enable Crescendo, TAP, and PAIR as probe families with Insidia Labs ids.
- DeepTeam worker image: `model_callback` awaits the hub. Use it for vulnerability classes we do not already cover via garak/promptfoo. Skip duplicates in the profile so we do not pay twice.

### Model service (`engine/models`)
Full design in [19-model-hosting.md](19-model-hosting.md).
- Move the model service from Stage 0 (llama.cpp + GGUF on one 20 GB GPU) to Stage 1: vLLM serving an AWQ build of the pinned uncensored model on a 48 GB GPU, so iterative attacks get batched throughput. Build the AWQ weights and verify them against the GGUF build before the switch.
- Build the model harness ([19-model-hosting.md](19-model-hosting.md#model-harness-enginemodelsharness)) before M-A11: role client with structured output, iterative loop runner, metering, transcripts. M-A11 is built on it; PyRIT and the Phase 5 agent use its role client.
- Callers request a role (`attacker`, `judge`), never a model name. The endpoint is OpenAI-compatible in both stages, so the switch is config.
- Decide from the calibration benchmark whether `judge` stays on the attacker model or moves to its own model and card. No commercial judge for attack transcripts; they refuse.
- Per-scan token meter writes `usage_events`. Budget pause from Phase 1 applies.
- Cache identical generation requests per profile version to cut cost. Do not cache target responses across orgs.

### Gray box
Target gains an optional context object the customer pastes or uploads in the dashboard: system prompt, tool schemas, purpose statement, sample docs. Stored encrypted per tenant.
Planner builds a targeted probe set: "exfiltrate via tool X", "ignore the stated purpose". Context is sent to our model service, not to the runner.

### Indirect injection and RAG (surfaces B and D)
- Hosted content the target can fetch: we publish a page or file containing a canary instruction, on a scan-scoped URL.
- Delivery modes in this phase: web page, uploaded document the customer ingests into their staging RAG, and a tool-result string if the target template can substitute tool output.
- Memory: if the target exposes a memory write/read in the template, plant on turn 1 and check obedience on a fresh session turn N.
- Corpus poisoning and cross-chunk smuggling are in the RAG profile. Tenant bleed is an ACL oracle: two planted docs in two tenants, ask as tenant A for tenant B's canary.

### Output sinks (LLM10)
Sink simulators run in our cloud, not on the customer host: HTML renderer that flags script execution, a shell parser that flags metacharacters in a tool arg, a second-model prompt that flags "instructions from the previous model". They consume the relay response. They do not browse the customer's production UI unless the customer points a tunnel target at a staging render endpoint.

### Unbounded consumption (LLM06)
Probes with a hard cap: max turns, max tool loops, max tokens. The oracle fires if the target keeps calling tools or inflating tokens past the declared budget. The scan's own budget still wins, so we cannot DoS ourselves.

### Transports to finish
Anthropic, Azure OpenAI, and Bedrock request templates if design partners need them. These are target transports only. Customers never bring their own attacker or judge model; the Stage 0 llama.cpp server doubles as the dev and CI model.

## Track 4B — classic depth

### API security
- OpenAPI import (customer uploads a spec; we do not crawl their repo yet).
- Auth: in runner mode, the runner holds the credential reference (header, cookie, or OAuth client credentials against a token URL) and the cloud stores only the reference, encrypted. In direct mode, credentials follow the [customer secrets](14-database-schema.md#customer-secrets) options and are decrypted only in the egress proxy.
- Checks: BOLA/IDOR (two identities, swap ids), broken auth, mass assignment, GraphQL introspection and batching, REST method tampering. These are Insidia Labs modules M-C3 and M-C4, because no engine we use does them.
- Identity B is a second credential on the target (`identity_b`), resolved on the runner or in the egress proxy.

### SAST, secrets, SCA
Runner does not scan. Customer uploads a source bundle or the runner `extract` precursor sends a tar of the repo **after** a denylist (`.git`, `.env`, `node_modules`). Prefer: runner hashes files and uploads only manifests plus a secret **finding location** (file, line, rule id), never the secret value.
- gitleaks for secrets (location only).
- osv-scanner and Trivy for lockfiles and container images the customer pushes to us.
- Bandit (Python) and gosec (Go) as optional packs.
- tree-sitter rules we write: string passed from an LLM client into `exec`, SQL, or HTML sinks. Small ruleset, tested on fixtures.

### Infra CVEs
Nuclei network templates against allowlisted hosts only, through the tunnel. No subnet sweep. The target allowlist is explicit IPs and hostnames.

Adopt naabu and tlsx for port and TLS checks.
- The sections above describe what each track must achieve; these modules are how the gaps in the engines are closed. Where an engine already covers a row well, we do not build.

## Tests
- Every new module passes its benchmark row in [16-coverage-gaps.md](16-coverage-gaps.md#validating-this-analysis) before it is enabled in a default profile.
- Clean-room review recorded on every M-C2 pull request.
- Gray-box vs black-box comparison on the benchmark app, checked into `engine/workers/ai/testdata/`.
- Calibration set precision test (nightly).
- BOLA fixture with two users.
- Secret fixture: value absent from API, object storage, and logs.
- Cross-org context object unreadable.

## Risks
- Hosted poisoned pages can be fetched by systems outside the test if the URL leaks. URLs are unguessable, single-scan, and expire.
- GPU cost. Cap concurrency on `ai.heavy` and record cost per scan before turning profiles on by default.
- No BF16 weights published for the chosen model blocks the AWQ build. Fallback: reproduce abliteration on the base model (see [19-model-hosting.md](19-model-hosting.md#building-vllm-weights)); until then Stage 0 keeps serving.
- Uploading repos fights the "thin runner" story. Keep upload optional and redacted; Phase 8 replaces bulk upload with artifact extraction.
