Status: approved direction, 10 Oct 2026. Site placement is in [24-site-redesign.md](24-site-redesign.md). These replace the HTML-player scripts in [22-website-video-scripts.md](22-website-video-scripts.md) and `site/src/content/video-script.md` for the homepage.

## Decisions (Rushi, 10 Oct 2026)

- We make both videos ourselves as rendered animations. No screen recording.
- The long-form video is about 3 minutes, not 8.
- No "open source" anywhere in either video.
- The sign-off matches the headline: "Your AI agent is your newest attack surface."

## How we make them

**Tool: HTML scenes rendered frame by frame with Playwright (Apache-2.0).** Each video is a timeline where every frame is a pure function of time. `render.mjs` seeks each frame in headless Chromium, takes a screenshot, and pipes it to the system `ffmpeg`. Motion Canvas was the first choice but only renders from its browser editor, with no headless command; Remotion is ruled out by its license.

**Where it lives:** `site/video/`, its own `package.json`, outside the Astro build.

```
site/video/
  package.json          playwright (Apache-2.0), the only dependency
  render.mjs            serves src/, renders frames, encodes, writes captions, poster, transcript, music
  src/
    stage.html          1920×1080 stage; ?v=howto or ?v=film; &preview adds a scrubber
    stage.css           brand colors and fonts from site/src/design/tokens.css
    engine.js           timeline, scenes, captions, chapter labels, watermark
    components.js       Terminal, CodePane, browser + report, chat, finding card, end card
    shared.js           scan output in ScanView's order; the headline
    howto.js, film.js   the two videos
    data/session.json   CLI output the videos read (placeholder until capture)
```

Commands, from `site/video/`: `npm run preview` (scrub in a browser), `npm run render` (drafts into `out/`), `node render.mjs howto film --publish` (writes `site/public/video/`, refuses placeholder data), and `node render.mjs film --snap=12,40` (single frames for review). `CHROMIUM_PATH` can point at an already-downloaded Chromium.

**Output:** `howto.{mp4,webm,jpg,vtt}`, `film.{mp4,webm,jpg,vtt}`, `film-chapters.vtt`, and a transcript per video. 1920×1080, 30 fps.

**Fonts:** Sora from `site/public/fonts/` for titles and captions. DejaVu Sans Mono for terminal text.

**Sound:** captions only, no voiceover. A soft background pad generated by `ffmpeg` from sine tones in `render.mjs`, so there is no third-party track or license to track. Every line in the scripts below is an on-screen caption, so the video works muted. The end-card caption is kept in the `.vtt` file but not drawn, because the end card already shows the headline.

### Keeping it honest without a recording

Plan 23 F18 asked for a real recording. The replacement rule: **every terminal line, report field, and finding in the videos comes from captured output of the real CLI.**

- A capture script (still to write, after F14) runs the CLI against the demo app with `--no-color`, recording each command, its output, its exit code, and how long it took. It also copies the finding fields from `findings.json` and the report summary. It writes all of that to `src/data/session.json` along with the CLI version and git commit.
- Scenes read CLI text only from `session.json`. Diagrams, captions, and the chat and PDF scenes are the only hand-written content.
- Until F14 exists, `session.json` is a placeholder marked `"placeholder": true`, written in the CLI's real output format. Placeholder renders get a "Draft · placeholder data" watermark, and `--publish` refuses to write into `site/public/video/` while that flag is set.
- Scenes that compress time show a "Sped up" badge.
- Plan 23 F18 gets a note that rendering from captured output replaces the recording requirement.

### Content rules

- Policy L1 only. No SQL injection or XSS result (the CLI has no such check). No AI-to-AppSec chain shown as a finding; the film shows it only as a diagram labeled "Illustrative".
- Do not use the 9 Oct Juice Shop template-injection run. The product review showed that detector fires on a harmless "49".
- Targets on screen: `localhost`, `127.0.0.1`, `staging.example.com`. Secrets only as `[AWS_ACCESS_KEY len=20 fp=3f9a1c07]`.
- Engines are named only if they ran in the captured scan or are on the verified list (F07).
- The demo app is a support bot that reads uploaded files, plus an orders API. The planned failing finding is an indirect prompt injection: a hidden line in an uploaded PDF makes the bot reveal a canary planted in its system prompt. If F08 doesn't promote that check, use whichever AI finding passes F08; the scene structure stays the same.
- `[BRACKETS]` mark values that come from `session.json`.

### Look

Navy `#101028` stage, terminal on Navy 800 `#181839`, orange `#ED7B39` highlights and cursor, magenta `#E33D86` for the failing row and the injected line, severity colors from `tokens.css`. Terminal text at least 28 px at 1080p. Motion is eased, never bouncy; one thing moves at a time. Captions sit in a band at the bottom, one line at a time.

## Build order

1. Scaffold `site/video/` with Motion Canvas, `theme.ts`, and fonts. Render one test frame to check color and type against the site.
2. Build the components, starting with `Terminal` and `ScanRow`, because both videos use them most.
3. Write a placeholder `session.json` in the exact shape `capture.py` will produce, with every value taken from the CLI's real output format (`ScanView` in `core/insidia/ui.py`, the `doctor` lines, `rerun` messages).
4. Build the how-to scenes. Render a watermarked draft MP4 for your review.
5. Build the film scenes. Render a watermarked draft for review.
6. Write `capture.py` and `encode.sh`. Once F14 exists, run the capture, rerender both videos, and remove the watermark.
7. Add `VideoModal.tsx` and `/film` to the site (plan 24), with captions and transcript.

Drafts (steps 4 and 5) need no F14 work and can start now. Only the final render waits for real captured data.
